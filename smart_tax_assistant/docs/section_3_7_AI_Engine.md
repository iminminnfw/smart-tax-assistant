# 3.7 ระบบปัญญาประดิษฐ์สำหรับการวางแผนภาษี (AI Tax Optimization Engine)

ระบบ Smart Tax Assistant ได้พัฒนา AI Engine สำหรับการวิเคราะห์และวางแผนภาษีแบบเฉพาะบุคคล โดยมีสถาปัตยกรรมที่ประกอบด้วยหลายส่วนทำงานร่วมกัน ตั้งแต่การคำนวณภาษีตามกฎหมาย การดึงข้อมูลกองทุนจากสำนักงานคณะกรรมการกำกับหลักทรัพย์และตลาดหลักทรัพย์ (ก.ล.ต.) แบบ Real-time ไปจนถึงการใช้ Generative AI สร้างคำแนะนำเฉพาะบุคคล

## 3.7.1 สถาปัตยกรรมของ AI Engine

ระบบ AI Engine ถูกพัฒนาเป็น Backend แยกต่างหากจาก Next.js โดยใช้ Python FastAPI เนื่องจากมีความเหมาะสมกับงานด้าน AI และการประมวลผลข้อมูลทางการเงิน ดังนี้

1. ระบบ Ecosystem ของ Python มีไลบรารีด้าน AI/ML ที่ครอบคลุม เช่น LangChain, OpenAI SDK, PyThaiNLP, BERTScore เป็นต้น
2. FastAPI รองรับ Asynchronous I/O ทำให้สามารถเรียก SEC API หลายตัวพร้อมกันได้อย่างมีประสิทธิภาพ
3. สามารถแยกการพัฒนาและ Deploy ได้อิสระจาก Frontend (Next.js) ตามหลัก Microservice Architecture

### ส่วนประกอบของ AI Engine

| ส่วนประกอบ | หน้าที่ | เทคโนโลยี |
|---|---|---|
| Tax Calculator Service | คำนวณภาษีตามกฎหมาย ม.40(6) และ 40(8) | Python |
| RAG Service | ดึงข้อมูลกฎหมายภาษีจาก Vector Database | Qdrant + LangChain |
| SEC API Client | ดึงข้อมูลกองทุนรวมจาก ก.ล.ต. แบบ Real-time | curl_cffi + AsyncIO |
| Smart Fund Analyzer | วิเคราะห์กองทุนเชิงลึก 4 มิติ | Python |
| AI Tax Advisor | สร้างคำแนะนำเฉพาะบุคคลด้วย LLM | OpenAI API |
| Rule-Based Parser | แปลงเป้าหมายจากภาษาธรรมชาติ (Fallback) | Regular Expression |
| Evaluation Service | วัดผลความถูกต้องของ AI | ROUGE, BLEU, BERTScore |

### กระบวนการทำงาน (Processing Flow)

1. ผู้ใช้กรอก Financial Profile (อายุ, อาชีพ, รายได้, ค่าใช้จ่าย, ความเสี่ยงที่รับได้) และระบุเป้าหมายในรูปแบบภาษาธรรมชาติ
2. Tax Calculator Service คำนวณภาษีปัจจุบันตามกฎหมาย ม.40(6) หรือ 40(8) อย่างแม่นยำ
3. RAG Service ดึงกลยุทธ์การลดหย่อนที่เกี่ยวข้องจาก Qdrant Vector Database
4. SEC API Client ดึงข้อมูลกองทุน RMF/ThaiESG แบบ Real-time จาก ก.ล.ต.
5. Smart Fund Analyzer วิเคราะห์กองทุนเชิงลึก 4 มิติ (Exposure, Performance, Tax Trap, Compliance)
6. AI Tax Advisor Engine ใช้ LLM รวมข้อมูลทั้งหมดแล้วสร้าง 3 สถานการณ์จำลอง (Scenarios) พร้อมเหตุผลประกอบ
7. ระบบส่งผลลัพธ์กลับในรูปแบบ JSON เพื่อแสดงเป็น Generative Dashboard บนหน้าเว็บ

## 3.7.2 การใช้งาน RAG ภายในระบบ

### 3.7.2.1 ทฤษฎีหลักการทำงานของ RAG

RAG (Retrieval-Augmented Generation) คือเทคนิคที่ใช้เป็นข้อมูลส่วนเสริมสำหรับเพิ่มความถูกต้องและความน่าเชื่อถือให้กับ Generative AI โดยการดึงข้อมูลจากแหล่งข้อมูลภายนอกมาผนวกเข้ากับ Prompt ก่อนที่ LLM จะสร้างคำตอบ

โดยหลักการทำงานสำคัญมีดังนี้

1. **Retrieval** เมื่อมีคำถามเข้ามา ระบบจะทำการค้นหาข้อมูลจากแหล่งข้อมูล เช่น เอกสารกฎหมายภาษี เอกสารเทคนิคการลดหย่อนภาษี โดยใช้วิธีการจัดทำดัชนี (Indexing) และเทคนิคการค้นหาแบบ Semantic Search
2. **Augmented Generation** เมื่อได้รับข้อมูลที่เกี่ยวข้องแล้ว Generative AI จะนำข้อความที่ Retrieve มาได้ผนวกรวมกับ Prompt เพื่อให้การสร้างคำตอบมีความถูกต้องและอ้างอิงจากข้อมูลจริง

### 3.7.2.2 เหตุผลในการเลือกใช้ RAG ภายในโครงงาน

การเลือกใช้ RAG สำหรับโครงงานนี้มีเหตุผลดังนี้

1. ข้อมูลการลดหย่อนภาษีอาจมีการเปลี่ยนแปลงในทุกปี การใช้ RAG ช่วยให้ข้อมูลมีความยืดหยุ่นได้มากกว่าการทำ Fine-tuning ซึ่งต้องเทรนโมเดลใหม่ทุกครั้งที่มีการเปลี่ยนแปลง
2. การใช้ RAG ช่วยให้ AI สามารถอ้างอิงเอกสารกฎหมายเป็นหลักฐานได้ดีกว่าการ Fine-tuning ซึ่งเหมาะกับการใช้เป็นแหล่งข้อมูลให้ Generative AI ช่วยในการตัดสินใจ
3. สามารถเพิ่มหรือปรับปรุงข้อมูลใน Vector Database ได้โดยไม่ต้องเทรนโมเดลใหม่

### 3.7.2.3 ข้อมูลที่ใช้สำหรับการใส่ใน RAG

ข้อมูลที่คัดเลือกเพื่อใส่เข้าไปใน RAG เพื่อช่วยในการแนะนำการลดหย่อนภาษีมีดังนี้

1. ความแตกต่างของภาษีเงินได้ประเภทที่ 6 และ 8
2. ตารางการเลือกค่าใช้จ่ายตามประเภทวิชาชีพและธุรกิจ
3. ตารางวิธีการลดหย่อนภาษีในปี 2568
4. กลยุทธ์ตามระดับรายได้และอาชีพ
5. กลยุทธ์พิเศษสำหรับการลดหย่อนค่าใช้จ่ายตามจริง VS แบบเหมา

(รูปที่ 3.x รูปตัวอย่างข้อมูลที่ใส่ใน Vector Database)

### 3.7.2.4 การเชื่อมต่อ Qdrant Vector Database

ระบบเชื่อมต่อกับ Qdrant Vector Database ผ่าน LangChain โดยใช้ OpenAI Embeddings ในการแปลงข้อมูลกฎหมายภาษีให้เป็น Vector เพื่อใช้ในการ Semantic Search ขั้นตอนการทำงานมีดังนี้

1. ข้อมูลกฎหมายภาษีถูกแปลงเป็น Embedding ผ่าน OpenAI Embeddings Model
2. จัดเก็บ Embedding ลงใน Qdrant Vector Database ที่รันบน Docker Container
3. เมื่อมี Request เข้ามา ระบบจะทำ Similarity Search เพื่อดึงข้อมูลที่มีความหมายใกล้เคียงกับคำถามมากที่สุด
4. ข้อมูลที่ได้จะถูกส่งเป็น Context ให้กับ LLM เพื่อสร้างคำตอบที่อ้างอิงจากกฎหมายจริง

**เทคโนโลยีที่ใช้:**

| เทคโนโลยี | หน้าที่ |
|---|---|
| Qdrant | Vector Database สำหรับจัดเก็บและค้นหา Embedding |
| LangChain | Framework สำหรับเชื่อมต่อ LLM กับ Vector Database |
| OpenAI Embeddings | แปลงข้อความภาษาไทยเป็น Vector |
| Docker | รัน Qdrant เป็น Container |

## 3.7.3 ระบบคำนวณภาษี (Tax Calculator Service)

เนื่องจากในโครงงาน 1 พบว่าการให้ Generative AI คำนวณภาษีโดยตรงนั้นอาจเกิดความผิดพลาดในเชิงตัวเลข (AI Hallucination) จึงได้พัฒนา Tax Calculator Service แยกออกมาเป็น Deterministic Module ที่คำนวณภาษีตามกฎหมายอย่างแม่นยำ 100% ก่อนส่งผลลัพธ์ให้ AI ใช้ประกอบการสร้างคำแนะนำ

### 3.7.3.1 เหตุผลที่แยก Tax Calculator ออกจาก AI

1. ป้องกัน AI Hallucination ในการคำนวณตัวเลข เนื่องจาก LLM มักคำนวณเลขผิดเมื่อมีหลายขั้นตอน
2. ผลการคำนวณถูกต้อง 100% ตามกฎหมาย เพราะเป็น Deterministic Algorithm
3. สามารถเขียน Unit Test ตรวจสอบผลลัพธ์ได้ง่ายและครอบคลุมทุกกรณี
4. ลดจำนวน Token ที่ต้องใช้ใน LLM Prompt เนื่องจากส่งเฉพาะผลลัพธ์การคำนวณไปให้ AI แทนที่จะให้ AI คำนวณเอง

### 3.7.3.2 การหักค่าใช้จ่ายตามประเภทเงินได้

Tax Calculator รองรับการหักค่าใช้จ่ายครบทุกประเภทตามที่กรมสรรพากรกำหนด ดังนี้

|---|---|---|

| ม.40(2) รับจ้างทำงาน | ไม่มีค่าใช้จ่ายให้หัก | |
| ม.40(3) ค่าลิขสิทธิ์ ค่ากู๊ดวิลล์ | 50% สูงสุด 100,000 บาท | |

ผู้ใช้สามารถเลือกหักค่าใช้จ่ายได้ 2 วิธี คือ แบบเหมา (ตามอัตราข้างต้น) หรือแบบตามจริง (ต้องมีหลักฐาน) โดยเลือกได้เพียงวิธีเดียว

### 3.7.3.3 การคำนวณภาษี 2 วิธีตามกฎหมาย

สำหรับเงินได้ตามมาตรา 40(6) และ 40(8) กฎหมายกำหนดให้คำนวณภาษี 2 วิธี แล้วเลือกจำนวนที่สูงกว่าเป็นภาษีที่ต้องชำระ

**วิธีที่ 1: คำนวณจากเงินได้สุทธิ (อัตราก้าวหน้า)**

```
เงินได้สุทธิ = เงินได้พึงประเมิน - ค่าใช้จ่าย - ค่าลดหย่อน
ภาษี = คำนวณตามอัตราขั้นบันได (0-35%)
```

**วิธีที่ 2: คำนวณ 0.5% ของเงินได้พึงประเมิน (Alternative Minimum Tax)**

```
ภาษี = เงินได้พึงประเมิน × 0.5%
```

**ภาษีที่ต้องชำระ = จำนวนที่สูงกว่าระหว่างวิธีที่ 1 กับวิธีที่ 2**

ยกเว้นกรณีเงินได้พึงประเมินไม่เกิน 1,000,000 บาท ให้เสียภาษีตามวิธีที่ 1 เพียงวิธีเดียว

## 3.7.4 การเชื่อมต่อ SEC Open API

### 3.7.4.1 ภาพรวมของ SEC Open API

SEC Open API คือ Application Programming Interface ที่ให้บริการโดยสำนักงานคณะกรรมการกำกับหลักทรัพย์และตลาดหลักทรัพย์ (ก.ล.ต.) สำหรับเข้าถึงข้อมูลกองทุนรวมในประเทศไทยแบบ Real-time ระบบ Smart Tax Assistant เชื่อมต่อกับ SEC Open API เพื่อดึงข้อมูลกองทุนรวมประเภทลดหย่อนภาษี (RMF และ ThaiESG) มาใช้ในการแนะนำการลงทุนให้ผู้ใช้

**ข้อมูลทั่วไปของ SEC Open API:**

| รายการ | รายละเอียด |
|---|---|
| Base URL | https://api.sec.or.th/v1 |
| Authentication | API Key (Ocp-Apim-Subscription-Key) |
| Rate Limit | 5,000 requests ต่อ 300 วินาที |
| Pagination | 100 รายการต่อหน้า (กำหนดโดย ก.ล.ต.) |
| Response Format | JSON |

### 3.7.4.2 API Endpoints ที่ใช้ในระบบ

ระบบ Smart Tax Assistant ใช้ SEC Open API จำนวน 8 Endpoints ดังนี้

| API | Endpoint | ข้อมูลที่ได้ | การนำไปใช้ในระบบ |
|---|---|---|---|
| Fund List | /fund/general-info | รายชื่อกองทุนทั้งหมดที่จดทะเบียนกับ ก.ล.ต. | กรองเฉพาะกองทุน RMF และ ThaiESG |
| API 3 | Specifications | ข้อมูลจำเพาะกองทุน (spec_code) | ตรวจจับ Feeder Fund (CIV, FIF, FOF) |
| API 6 | Factsheet URLs | ลิงก์เอกสาร Factsheet PDF ทางการ | แนบหลักฐานจาก ก.ล.ต. ในทุกคำแนะนำ |
| API 8 | Benchmark | ชื่อดัชนีอ้างอิง (Benchmark) ของกองทุน | วิเคราะห์ Alpha ว่าชนะหรือแพ้ดัชนีอะไร |
| API 12 | Statistics | ค่าสถิติทางการเงิน (Alpha, Beta, Sharpe Ratio) | วิเคราะห์ประสิทธิภาพและความเสี่ยงกองทุน |
| API 13 | Dividend Policy | นโยบายการจ่ายเงินปันผล (Y หรือ N) | วิเคราะห์ Tax Efficiency ของกองทุน |
| API 15 | Performance | ผลตอบแทนย้อนหลัง (1 ปี / 3 ปี / 5 ปี) | เปรียบเทียบผลตอบแทนระหว่างกองทุน |
| API 20 | Daily NAV | มูลค่าหน่วยลงทุนล่าสุด (Net Asset Value) | แสดงราคาปัจจุบันของกองทุน |

### 3.7.4.3 กลไกควบคุมอัตราการเรียก API (Rate Limiting)

SEC Open API มีข้อจำกัดในการเรียกใช้งานอยู่ที่ 5,000 Requests ต่อ 300 วินาที หากเรียกเกินจำนวนที่กำหนด จะได้รับ HTTP Status Code 421 (Rate Limit Exceeded) ระบบจึงได้พัฒนา SEC Rate Limiter เพื่อควบคุมการเรียก API ให้อยู่ภายในขอบเขตที่ ก.ล.ต. กำหนด

**กลไกการทำงาน:**

1. **Sliding Window Algorithm:** ใช้โครงสร้างข้อมูล deque เก็บ timestamp ของทุก Request ภายในช่วง 300 วินาที เมื่อจำนวน Request เข้าใกล้ขีดจำกัด ระบบจะชะลอการส่ง Request ใหม่โดยอัตโนมัติ
2. **Minimum Interval:** กำหนดระยะห่างขั้นต่ำ 20 มิลลิวินาที ระหว่างแต่ละ Request เพื่อป้องกันการส่ง Request ถี่เกินไป
3. **HTTP 421 Handling:** เมื่อได้รับ HTTP 421 ระบบจะอ่านค่า Retry-After จาก Response Header แล้วรอตามเวลาที่ ก.ล.ต. กำหนดก่อนส่ง Request ใหม่
4. **Exponential Backoff:** หาก Request ล้มเหลวจากข้อผิดพลาดของเซิร์ฟเวอร์ (HTTP 5xx) ระบบจะรอเพิ่มขึ้นเป็นทวีคูณ (2, 4, 8 วินาที) ก่อนลองใหม่
5. **Max Retries:** พยายามส่ง Request ซ้ำสูงสุด 3 ครั้ง หากยังไม่สำเร็จจะหยุดและแจ้งข้อผิดพลาด

(รูปที่ 3.x แผนผังการทำงานของ SEC Rate Limiter)

```
Request เข้ามา
     │
     ▼
┌──────────────┐     เกิน Limit     ┌─────────────────┐
│ ตรวจสอบ       │ ─────────────────▶ │ รอจนกว่าจะ       │
│ Sliding Window│                    │ ว่างภายใน Window │
└──────┬───────┘                    └────────┬────────┘
       │ ผ่าน                                │
       ▼                                     │
┌──────────────┐                             │
│ ตรวจสอบ       │◀────────────────────────────┘
│ Min Interval  │
└──────┬───────┘
       │ ผ่าน
       ▼
┌──────────────┐
│ ส่ง Request   │
│ ไปยัง SEC API │
└──────┬───────┘
       │
       ▼
┌──────────────────────────────────────────────┐
│ HTTP 200 (สำเร็จ)  → คืนค่า JSON            │
│ HTTP 421 (Rate Limit) → รอ Retry-After → ลอง│
│ HTTP 5xx (Server Error) → Backoff → ลองใหม่  │
│ ครบ 3 ครั้ง → แจ้งข้อผิดพลาด                  │
└──────────────────────────────────────────────┘
```

### 3.7.4.4 การจัดการข้อมูลกองทุนลดหย่อนภาษี (Tax Fund Service)

Tax Fund Service ทำหน้าที่กรองข้อมูลจาก SEC API เพื่อคัดเลือกเฉพาะกองทุนที่สามารถใช้ลดหย่อนภาษีได้ในปี 2568 โดยแบ่งเป็น 2 ประเภทหลัก

| ประเภทกองทุน | Keywords สำหรับกรอง | เพดานลดหย่อน |
|---|---|---|
| RMF (กองทุนรวมเพื่อการเลี้ยงชีพ) | "RMF", "RETIREMENT", "เพื่อการเลี้ยงชีพ", "กองทุนรวมเพื่อการเลี้ยงชีพ" | 30% ของรายได้ สูงสุด 500,000 บาท |
| ThaiESG (กองทุนรวมไทยเพื่อความยั่งยืน) | "THAIESG", "THAI ESG", "ESG", "ไทยอีเอสจี", "ธรรมาภิบาล" | 30% ของรายได้ สูงสุด 300,000 บาท |

**หมายเหตุ:** SSF (กองทุนรวมเพื่อการออม) ไม่รวมอยู่ในระบบ เนื่องจากหมดสิทธิ์ลดหย่อนตั้งแต่ 31 ธันวาคม 2567

Tax Fund Service ยังมีความสามารถในการคำนวณจำนวนภาษีที่ประหยัดได้ (Tax Savings) จากการลงทุนในกองทุนลดหย่อน โดยใช้อัตราภาษีขั้นบันไดเดียวกับ Tax Calculator Service

### 3.7.4.5 การใช้ Browser Impersonation

เนื่องจาก SEC Open API มีระบบตรวจจับ Bot ที่ตรวจสอบ TLS Fingerprint ของ HTTP Client ระบบจึงใช้ไลบรารี curl_cffi แทน Requests หรือ HTTPX ทั่วไป เนื่องจาก curl_cffi มีความสามารถในการจำลอง TLS Fingerprint ของเว็บเบราว์เซอร์จริง (Browser Impersonation) ทำให้ Request มีลักษณะเหมือนการเข้าถึงจากเว็บเบราว์เซอร์ Chrome 110 แทนที่จะเป็น Python HTTP Client

### 3.7.5.1 Layer 1: True Exposure Intelligence (ตรวจจับกองทุนซ้อนกองทุน)

ใช้ข้อมูลจาก API 3 (Specifications) ตรวจสอบ spec_code ของกองทุนเพื่อวิเคราะห์ว่ากองทุนนั้นลงทุนโดยตรงหรือลงทุนผ่านกองทุนอื่นอีกชั้นหนึ่ง ซึ่งมีผลต่อค่าธรรมเนียมและความเสี่ยงที่แท้จริง

| ประเภท | รหัส spec_code | ความหมาย | ความเสี่ยงที่ตรวจพบ |
|---|---|---|---|
| Feeder Fund | CIV | กองทุนรวมที่ลงทุนในกองทุนรวมอื่น | ค่าธรรมเนียมซ้อนกัน 2 ชั้น |
| Foreign Fund | FIF | กองทุนที่ลงทุนในต่างประเทศ | ความเสี่ยงจากอัตราแลกเปลี่ยน (FX Risk) |
| Fund of Funds | FOF | กองทุนที่ลงทุนในกองทุนอื่นเป็นหลัก | ค่าธรรมเนียม 2 ชั้นและความโปร่งใสต่ำ |

นอกจากนี้ระบบยังตรวจสอบว่ากองทุนลงทุนใน Master Fund ต่างประเทศใด โดยค้นหา Keywords เช่น ARK, BlackRock, Vanguard, iShares, PIMCO, JPMorgan, Goldman Sachs, Fidelity, Schroders เป็นต้น เพื่อให้ผู้ใช้ทราบว่าเงินลงทุนจริงๆ ไปอยู่ที่ไหน

### 3.7.5.2 Layer 2: Relative Performance Intelligence (วิเคราะห์ผลตอบแทนเทียบ Benchmark)

ใช้ข้อมูลจาก API 8 (Benchmark) ร่วมกับ API 12 (Statistics) วิเคราะห์ว่าผู้จัดการกองทุนสร้างมูลค่าเพิ่มได้จริงหรือไม่ โดยเทียบกับดัชนีอ้างอิง

| ค่าสถิติ | เกณฑ์ | ความหมาย |
|---|---|---|
| Alpha > 0 | ชนะ Benchmark | ผู้จัดการกองทุนสร้างมูลค่าเพิ่มได้ดี |
| Alpha < 0 | แพ้ Benchmark | ควรพิจารณากองทุน Passive (Index Fund) แทน |
| Beta < 1 | ผันผวนน้อยกว่าตลาด | เหมาะกับผู้ที่รับความเสี่ยงต่ำ |
| Beta > 1 | ผันผวนมากกว่าตลาด | เหมาะกับผู้ที่รับความเสี่ยงสูงและต้องการผลตอบแทนที่สูง |
| Sharpe Ratio > 1 | Risk-adjusted Return ดี | ผลตอบแทนคุ้มค่าเมื่อเทียบกับความเสี่ยงที่รับ |
| Sharpe Ratio < 0.5 | Risk-adjusted Return ต่ำ | ผลตอบแทนไม่คุ้มค่ากับความเสี่ยง |

ระบบจะแสดงชื่อ Benchmark จริง เช่น SET TRI (Total Return Index), MSCI World ควบคู่กับค่า Alpha เพื่อให้ผู้ใช้เข้าใจว่ากองทุนชนะหรือแพ้ดัชนีอะไร ไม่ใช่แค่แสดงตัวเลขเพียงอย่างเดียว

### 3.7.5.3 Layer 3: Tax Trap Intelligence (วิเคราะห์ผลกระทบภาษีจากเงินปันผล)

ใช้ข้อมูลจาก API 13 (Dividend Policy) วิเคราะห์นโยบายการจ่ายเงินปันผลของกองทุน เนื่องจากเงินปันผลจากกองทุนรวมจะถูกหักภาษี ณ ที่จ่าย 10% ซึ่งส่งผลให้ผลตอบแทนสุทธิลดลง โดยเฉพาะสำหรับผู้ที่มีฐานภาษีสูง

| นโยบาย | รหัส | Tax Efficiency | คำแนะนำ |
|---|---|---|---|
| Accumulating (สะสมมูลค่า) | N | สูง (Optimal) | แนะนำสำหรับผู้มีรายได้สูง เพราะไม่เสียภาษีเงินปันผล 10% มูลค่าหน่วยลงทุนเติบโตแทน |
| Distributing (จ่ายเงินปันผล) | Y | ต่ำกว่า (Suboptimal) | ระวัง Tax Leakage สำหรับผู้ที่อยู่ในฐานภาษี 25% ขึ้นไป เพราะจะเสียภาษีปันผลหัก ณ ที่จ่าย 10% ทำให้ได้ผลตอบแทนสุทธิน้อยลง |

**ตัวอย่างการคำนวณ Tax Leakage:**

สมมติผู้ใช้อยู่ในฐานภาษี 25% ลงทุนในกองทุน RMF ที่จ่ายเงินปันผล 50,000 บาท/ปี

```
เงินปันผลก่อนหักภาษี:    50,000 บาท
หักภาษี ณ ที่จ่าย 10%:   -5,000 บาท
เงินปันผลสุทธิ:          45,000 บาท
Tax Leakage ต่อปี:        5,000 บาท
```

หากเลือกกองทุน Accumulating (ไม่จ่ายปันผล) แทน จะไม่เสียภาษี 5,000 บาทนี้ และเงินจะถูกลงทุนต่อ (Compound) ซึ่งสร้างผลตอบแทนที่สูงกว่าในระยะยาว

### 3.7.5.4 Layer 4: Trust & Compliance Intelligence (แนบหลักฐานจาก ก.ล.ต.)

ใช้ข้อมูลจาก API 6 (Factsheet URLs) เพื่อเพิ่มความน่าเชื่อถือให้กับทุกคำแนะนำที่ระบบสร้างขึ้น โดยแนบหลักฐานทางการจาก ก.ล.ต.

| หลักฐานที่แนบ | รายละเอียด |
|---|---|
| PDF Factsheet | ลิงก์เอกสาร Factsheet ทางการจาก ก.ล.ต. สำหรับทุกกองทุนที่แนะนำ ผู้ใช้สามารถกดเพื่ออ่านข้อมูลเพิ่มเติมได้ |
| Data Freshness | แสดงวันที่ของข้อมูล (as_of_date) เพื่อให้ผู้ใช้ทราบว่าข้อมูลเป็นปัจจุบันเพียงใด หากข้อมูลเก่ากว่า 45 วัน จะแสดงคำเตือน |
| Regulatory Disclaimers | คำเตือนตามกฎหมาย เช่น "ผลการดำเนินงานในอดีตไม่ได้เป็นการรับประกันผลตอบแทนในอนาคต" และ "ผู้ลงทุนควรศึกษาข้อมูลก่อนการตัดสินใจลงทุน" |

## 3.7.6 AI Tax Advisor Engine

AI Tax Advisor Engine เป็นส่วนหลักที่ใช้ Generative AI (Large Language Model) ในการสร้างคำแนะนำการวางแผนภาษีแบบเฉพาะบุคคล โดยรับข้อมูลจาก Tax Calculator, RAG Service, SEC API และ Smart Fund Analyzer มารวมกันแล้วสร้างคำแนะนำที่เข้าใจง่ายและมีเหตุผลประกอบ

ระบบรองรับ LLM หลายตัว:
- **OpenAI GPT-4o** เป็น LLM หลักสำหรับ Production
- **Anthropic Claude** เป็นทางเลือกสำรอง

### 3.7.6.1 Goal Parser (แปลงเป้าหมายจากภาษาธรรมชาติ)

ระบบรับเป้าหมายจากผู้ใช้ในรูปแบบภาษาธรรมชาติ (ทั้งภาษาไทยและอังกฤษ) แล้วใช้ LLM แปลงเป็น Structured Data เพื่อให้ระบบประมวลผลต่อได้

| ประเภทเป้าหมาย (GoalType) | ตัวอย่าง Input ภาษาธรรมชาติ | Structured Output |
|---|---|---|
| Tax Saving | "อยากประหยัดภาษี 80,000 บาท" | goal_type: tax_saving, target_amount: 80,000 |
| Cash Flow | "ต้องมีเงินเหลือ 300,000 บาทต่อปี" | goal_type: cash_flow, target_amount: 300,000 |
| Life Event | "จะซื้อบ้าน 5 ล้าน ใน 3 ปี" | goal_type: life_event, target_amount: 5,000,000, deadline: 3 ปี |
| Retirement | "อยากเกษียณตอนอายุ 55" | goal_type: retirement, target_age: 55 |
| Hybrid | "ประหยัดภาษีสูงสุด แล้วก็อยากซื้อบ้านใน 2 ปี" | goal_type: hybrid, sub_goals: [tax_saving, life_event] |

### 3.7.6.2 Dynamic Scenario Generator (สร้างสถานการณ์จำลอง)

ระบบสร้าง 3 สถานการณ์ (Scenarios) ที่แตกต่างกัน โดยปรับตามโปรไฟล์และเป้าหมายของผู้ใช้แต่ละคน ไม่ใช่สถานการณ์ตายตัว

| สถานการณ์ | ลักษณะ | เหมาะกับ |
|---|---|---|
| Conservative (ระมัดระวัง) | ลงทุนน้อย เน้นความมั่นคงและสภาพคล่อง | ผู้ที่รับความเสี่ยงต่ำ หรือมีกองทุนฉุกเฉินน้อย |
| Balanced (สมดุล) | สมดุลระหว่างการลงทุนและสภาพคล่อง | ผู้ที่รับความเสี่ยงปานกลาง |
| Aggressive (เชิงรุก) | ลงทุนสูง เน้นลดหย่อนภาษีสูงสุด | ผู้ที่รับความเสี่ยงสูง มีเงินออมเพียงพอ |

แต่ละสถานการณ์จะประกอบด้วย:
- ยอดลงทุนรวมที่แนะนำ (บาท)
- สัดส่วนการลงทุนในแต่ละกองทุน (RMF, ThaiESG, ประกันชีวิต, ประกันบำนาญ)
- จำนวนภาษีที่ประหยัดได้ (บาท)
- เงินคงเหลือหลังลงทุน (บาท)
- คำอธิบายเหตุผลจาก AI ว่าทำไมถึงแนะนำแบบนี้

### 3.7.6.3 Profile-Based Analysis (วิเคราะห์ตามโปรไฟล์ผู้ใช้)

ระบบรับข้อมูล Financial Profile ของผู้ใช้เพื่อสร้างคำแนะนำที่เหมาะสมกับสถานการณ์จริงของผู้ใช้แต่ละคน

| ข้อมูล Profile | การนำไปใช้ในระบบ |
|---|---|
| อายุ | กำหนดระยะเวลาลงทุนใน RMF (ต้องถืออย่างน้อย 5 ปี หรือจนอายุ 55 ปี) |
| รายได้ต่อปี | คำนวณเพดานลดหย่อน RMF (30% ของรายได้) และ ThaiESG (30% ของรายได้) |
| ค่าใช้จ่ายต่อเดือน | ประเมินเงินที่เหลือสำหรับลงทุนได้จริง |
| เงินออมปัจจุบัน | ประเมินความพร้อมในการลงทุน |
| กองทุนฉุกเฉิน | ตรวจสอบว่ามีเงินสำรองเพียงพอก่อนลงทุน (แนะนำ 3-6 เดือนของค่าใช้จ่าย) |
| ความเสี่ยงที่รับได้ | เลือกประเภทกองทุน (หุ้น, ตราสารหนี้, ผสม) |
| อาชีพ | กำหนดประเภทเงินได้ ม.40(6) หรือ 40(8) และอัตราหักค่าใช้จ่ายเหมา |
| สถานะสมรส | คำนวณลดหย่อนคู่สมรส (60,000 บาท) |
| จำนวนบุตร | คำนวณลดหย่อนบุตร (30,000-60,000 บาทต่อคน) |
| การลดหย่อนที่มีอยู่แล้ว (RMF, ThaiESG, ประกัน) | คำนวณวงเงินลดหย่อนที่เหลืออยู่เพื่อไม่ให้แนะนำเกินเพดาน |

### 3.7.6.4 Reasoning Transparency (ความโปร่งใสในการอธิบาย)

จุดเด่นของระบบคือ AI จะอธิบายเหตุผลทุกครั้งว่าทำไมถึงแนะนำแบบนั้น ไม่ใช่แค่บอกว่า "ควรลงทุน RMF 200,000 บาท" แต่จะอธิบายว่า

- ทำไมถึงเลือกจำนวนนี้ (เช่น "เพราะ 30% ของรายได้ 1,200,000 = 360,000 แต่แนะนำ 200,000 เพื่อเหลือเงินสำรอง")
- ความเสี่ยงที่ต้องพิจารณา (เช่น "RMF ต้องถือจนอายุ 55 ปี คุณเหลืออีก 25 ปี")
- ผลกระทบทางภาษี (เช่น "ลงทุน 200,000 ประหยัดภาษีได้ 50,000 บาท เพราะอยู่ในฐานภาษี 25%")

## 3.7.7 Rule-Based Goal Parser (ระบบสำรอง)

เนื่องจาก LLM อาจไม่สามารถตอบสนองได้ทุกครั้ง เช่น ปัญหาเครือข่าย, API ล่ม, หมด Quota หรือใช้เวลาตอบนาน ระบบจึงพัฒนา Rule-Based Goal Parser เป็นระบบสำรอง (Fallback) ที่ทำงานด้วย Regular Expression โดยไม่ต้องพึ่งพา GPU หรือ Internet

### 3.7.7.1 กลไกการทำงาน

1. **ตรวจสอบ Intent จาก Keywords:** ค้นหาคำสำคัญในข้อความเพื่อระบุความต้องการของผู้ใช้

| Keywords | Intent ที่ได้ |
|---|---|
| "ลดหย่อนภาษี", "ประหยัดภาษี", "tax", "save tax" | tax_saving |
| "เงินสด", "สภาพคล่อง", "เงินสำรอง", "cash", "liquidity" | liquidity |
| (ไม่ตรงกับ keyword ใด) | balanced (ค่าเริ่มต้น) |

2. **ดึงจำนวนเงินจากข้อความ:** ใช้ Regular Expression `(\d+(?:,\d+)*(?:\.\d+)?)` เพื่อจับตัวเลขจำนวนเงิน

3. **วิเคราะห์บริบท:** ตรวจสอบคำรอบข้างตัวเลขเพื่อระบุว่าเป็น constraint ประเภทใด

| คำบริบท | ประเภท Constraint |
|---|---|
| "เหลือ", "เก็บ", "สำรอง" | min_liquidity (เงินที่ต้องเหลือขั้นต่ำ) |
| "ลงทุน", "มีเงิน" | max_budget (งบประมาณที่มีสำหรับลงทุน) |

### 3.7.7.2 ตัวอย่างการทำงาน

| Input ภาษาธรรมชาติ | Output (Structured) |
|---|---|
| "อยากลดหย่อนภาษี มีเงิน 500,000" | {intent: "tax_saving", max_budget: 500,000} |
| "ต้องการเก็บเงินสำรอง 200,000 บาท" | {intent: "liquidity", min_liquidity: 200,000} |
| "วางแผนการเงินทั่วไป" | {intent: "balanced", constraints: {}} |

### 3.7.7.3 ข้อจำกัดของ Rule-Based Parser

Rule-Based Parser มีข้อจำกัดเมื่อเทียบกับ LLM ดังนี้

| ด้าน | Rule-Based Parser | LLM (AI Tax Advisor) |
|---|---|---|
| ความเข้าใจภาษา | จำกัดเฉพาะ Keywords ที่กำหนดไว้ | เข้าใจภาษาธรรมชาติได้หลากหลาย |
| การจับ Intent ซ้อน | ไม่รองรับ Hybrid Goal | รองรับ Hybrid Goal ได้ |
| ความเร็ว | เร็วมาก (< 1ms) | ช้ากว่า (1-5 วินาที) |
| ต้องการ Internet | ไม่ต้องการ | ต้องการ (เรียก API) |
| ความน่าเชื่อถือ | ทำงานได้เสมอ (100% uptime) | ขึ้นอยู่กับ API availability |

ระบบจะใช้ LLM เป็นหลัก และใช้ Rule-Based Parser เป็น Fallback เมื่อ LLM ไม่ตอบสนองภายในเวลาที่กำหนด เพื่อให้ระบบทำงานได้ต่อเนื่องและผู้ใช้ไม่ต้องรอนาน
